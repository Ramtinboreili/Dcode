The Dcode guide

Dcode is a coding agent that runs in your terminal, with a matching web UI. It works with your own local or private LLMs, and it's built for models with small context windows (32K or less). This guide covers installing it, connecting a model, and day-to-day use.

v0.3.1Air-gapped friendlyTerminal + Web UIAny OpenAI-compatible server

1What Dcode does

Ask in plain language: "fix the failing test", "add a health endpoint", "explain this repo". Dcode reads your code, edits files, runs commands and checks git. It shows every step and asks before it runs anything risky.

Your models, your networkWorks with Ollama, vLLM, llama.cpp, LM Studio, TGI or any OpenAI-compatible endpoint. Nothing leaves your network.
Small-context smartReads only the lines it needs, trims old output and summarizes long chats, so 32K models stay sharp.
Helpers (sub-agents)Hands focused jobs to helpers (Explorer, Coder, Reviewer, Tester) that start with a clean slate.
Memory, artifacts, skillsRemembers your conventions, saves pages and diagrams for you to view, and follows reusable playbooks.

2Install

macOS (Apple Silicon)

Build a single self-contained binary from the source folder and install it. No sudo needed:

shell
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
make mac PYTHON=.venv/bin/python      # installs /opt/homebrew/bin/dcode
dcode --version

Linux servers (air-gapped)

Build on a connected machine with the same OS and CPU as the target (PyInstaller doesn't cross-compile), then copy two files over:

shell — build machine
make deb      # → dist/dcode and dist/dcode_0.3.1_<arch>.deb
shell — air-gapped server
sudo ./install-airgap.sh dcode_0.3.1_amd64.deb   # Debian / Ubuntu
sudo ./install-airgap.sh ./dcode                 # any Linux, copies to /usr/local/bin
💡

For a build machine without internet, pre-download wheels and run PIP_ARGS="--no-index --find-links ./wheels" make binary.

From source (any OS with Python 3.10+)

shell
pip install .
dcode

3Connect a model

The first time you run dcode, a short setup asks for the server URL, an API key (any text works for local servers), the model and its context window. You can also configure it with environment variables, which is best for servers and shared machines:

Ollama
export DCODE_BASE_URL=http://127.0.0.1:11434/v1
export DCODE_API_KEY=local
export DCODE_MODEL=qwen2.5-coder:7b
export DCODE_CONTEXT_WINDOW=32768
dcode
vLLM / llama.cpp
export DCODE_BASE_URL=http://gpu-node.internal:8000/v1   # llama-server: :8080/v1
export DCODE_API_KEY=local
export DCODE_MODEL=Qwen/Qwen2.5-Coder-7B-Instruct
dcode
⚠️

Set the context window to match your server (for example --ctx-size in llama.cpp or num_ctx in Ollama). Dcode uses it to decide when to trim and summarize.

4Using the terminal

Open a terminal in your project folder and run dcode. The welcome panel shows the model, folder and a web UI link. Type what you want and press Enter.

  • Each step shows as a line such as ⏺ read_file app.py. When a task finishes, Dcode writes a short report (what it did, files changed, commands run), followed by ✓ Done in 3.2s · 2 files changed · 3 commands.
  • The input box grows as you type. Press Enter to send; ⌥ Option/Alt+Enter (or \ then Enter) adds a new line; ↑/↓ recall earlier messages.
  • While Dcode works, Ctrl+C stops the current task and your chat stays intact. At an empty input box, press Ctrl+C twice to exit.
  • Each chat is named automatically from your first message. The name shows under the input box and in the web UI.
  • When Dcode wants to run a command, delete a file or commit, a menu appears. Choose with the arrow keys and Enter, or press y (allow), a (allow for this session) or n (deny).
  • In long lists, such as the model list, just type to filter.
  • Mention files with @: type @ and part of a name, then Tab or Enter to pick it, e.g. fix the bug in @src/app.py. Up to 3 mentioned files go straight into the conversation, so Dcode doesn't spend steps finding them. Works in the web UI too.
  • For longer tasks Dcode keeps a checklist (☰) and ticks steps off as it goes. The list survives "context compacted", so small models stay on track.
  • When something is genuinely unclear, Dcode may ask you a question with a few choices. Pick one, type your own answer, or press Esc to let it decide.

Your own commands

Save a prompt you use often as a Markdown file and it becomes a command. .dcode/commands/review-pr.md in a project (or ~/.dcode/commands/ for all projects) becomes /review-pr:

.dcode/commands/review-pr.md
---
description: Review my branch against main
agent: review            # optional: run it as this helper
---
Review these changes for bugs and missing tests. Focus: $ARGUMENTS
!`git diff main...HEAD --stat`
Our conventions are in @CONTRIBUTING.md

$ARGUMENTS is what you type after the command ($1, $2… single words). !`command` puts that command's output in the prompt; it follows the same mode and rules as Dcode's own commands, so it asks first unless allowed.

Modes

Press Shift+Tab in the input box to cycle modes. The current mode shows under the box, and the border color changes with it. You can also pick a mode in the web UI next to the message box.

ModeWhat Dcode may do
🔵 Accept edits (default)Edits files freely; asks before commands, deletions and commits
🟢 AutoNever asks. Use only in trusted or sandboxed projects
🟣 PlanRead-only: investigates and writes a plan, then asks "Ready to implement this plan?"
⚪ ManualAsks before every edit and every command

Output, undo and git

  • Command output shows the first few lines. Press Ctrl+O at the input box to see the full output of the last task.
  • Each edit shows a red/green preview of what changed.
  • Checks after edits: right after changing a file, Dcode checks it (syntax errors, undefined names) with what's already on your machine: Python itself, ruff, node, bash, gofmt and others. Problems go straight back to the model, which fixes them in its next step. Turn on Also format them in Settings → Permissions to run your formatter too.
  • While Dcode works, a live panel shows the current step, every running helper and background jobs, each with a timer. Long-running commands (servers, watchers) run as background jobs; the status line counts them and /jobs manages them. They stop when you exit.
  • Every task saves a checkpoint. /undo puts the files back as they were, even outside git.
  • /diff shows your uncommitted changes, and /commit writes a commit message from the diff and asks before committing.

5Using the web UI

Every dcode you start also opens a private page on your machine. Open the link from the welcome panel (or run dcode ui). Each user on a shared server gets their own private page.

  • Sidebar: live sessions on top, past chats grouped by date, plus search and New chat (⌘/Ctrl ⇧ O).
  • Chat: send tasks to the same session as your terminal. Steps fold into "Worked through N steps", and helpers show as cards.
  • Approvals: Allow, Allow for this session or Deny, from the browser or the terminal. Whichever answers first wins.
  • Model menu (top left): search the server's models or type any name; set reasoning effort.
  • Settings: connection, model, helpers, memory, permissions, skills, and light/dark/system theme.
💡

The page closes itself a few seconds after your last dcode exits. Chats, memory and artifacts stay on disk and appear again next time.

6Helpers (sub-agents)

For bigger jobs, Dcode hands self-contained tasks to helpers. Each one starts with an empty context and returns only a short report, which keeps the main conversation small and focused.

HelperGood for
🧭 ExplorerFinding and reading code; reports facts with file:line references (read-only)
💻 CoderMaking one well-defined change
👁 ReviewerChecking code or a diff for bugs (read-only)
🧪 TesterWriting and running tests

Read-only helpers can work in parallel. Set how many in /agents settings or Settings → Helpers. Running more than one at a time needs a server that handles concurrent requests (vLLM, or llama-server --parallel N).

  • Use one yourself: start a message with @name, e.g. @explore where is the login handled?. Only its report comes back.
  • A model for helpers: set Helper model in Settings → Helpers to run helpers on a smaller, faster model from the same server, while the main chat keeps the bigger one.
  • Make your own: add a Markdown file in ~/.dcode/agents/ or a project's .dcode/agents/, or use New helper in Settings → Helpers. A file named like a built-in (explore.md…) changes that helper.
.dcode/agents/ansible.md
---
description: Reviews Ansible playbooks for idempotency and secrets
tools: read-only          # or: edit, or a list like read_file, run_command
model: qwen2.5-coder:7b   # optional
steps: 20                 # optional
---
You review Ansible code. Check every task for idempotency, ...

7Memory

Dcode remembers useful facts between sessions: project conventions, how to run tests, your preferences, and short summaries of past work. Relevant memories are added to each new task automatically.

  • Tell it directly: "remember that we deploy with make release", or use /remember.
  • Browse, add and delete memories in the web UI (sidebar → Memory).
  • Everything is plain Markdown in ~/.dcode/memory/, stored per project or globally. It's searched offline with no embedding model.

8Artifacts

When you ask for something to look at, such as a dashboard, a diagram, a report or a long script, Dcode saves it as an artifact instead of pasting it into the chat.

  • A card appears in the chat. Click Open to see it in a side panel with Preview and Code tabs, Copy and Download.
  • All artifacts live in the Artifacts library in the sidebar.
  • Kinds: web pages (HTML), diagrams (SVG), documents (Markdown), tables (CSV) and code.
  • Pages run in a locked-down sandbox with no internet access. Every update keeps the previous version.

Managing artifacts

  • Library: live previews, search, filter by kind and sort. Each tile's menu has Open, Open as a page, Copy link, Rename, Duplicate, Download and Delete.
  • Viewer: Preview, Code and Edit tabs (saving creates a new version). Pick any version from the history and Restore it. Click the title to rename, and use the link to jump back to the chat that made it.
  • Ask Dcode to change it: type a request in the box under the viewer and Dcode updates the same artifact as a new version.
  • New artifact: ask Dcode to build one, write or paste one yourself, or upload a file (HTML, SVG, Markdown, CSV or any code).
  • Links: every artifact has its own page at /a/<id>. When Dcode saves one in the terminal, the link is printed, and /artifacts lists them and opens one in your browser.
try it
Make an HTML dashboard that shows the services in docker-compose.yml and their ports.

9Skills

Skills are short playbooks that shape how Dcode works. Only their names and one-line descriptions are in the prompt, and Dcode loads the full skill when it fits the task. That keeps them cheap even on small models. Pin a skill to always include it.

SkillUse it for
devopsDocker, Kubernetes, CI/CD, Terraform, shell, servers, done safely
developerFeatures and refactors with small, tested changes
ui-designerClean, accessible, responsive interfaces
code-reviewerFinding real bugs, security issues and missing tests
artifact-creatorPolished pages, dashboards, diagrams and reports

Make your own

  1. Ask Dcode: "make a skill for writing Ansible playbooks the way my team does". It writes and saves the skill.
  2. In the web UI: Settings → Skills → Create (Dcode writes it) or Write one yourself.
  3. As a file: drop a .md file into ~/.dcode/skills/, or into .dcode/skills/ inside a project to share it with your team through git.
~/.dcode/skills/ansible.md
---
name: ansible
description: Writing Ansible playbooks and roles our team's way.
---
# Ansible
- Use roles; one role per service.
- Every task has a name and tags.
- Secrets come from ansible-vault, never plain text.
- Check with --check --diff before applying.

10Databases

Save a connection to a database once, then browse it, query it, summarize it and export from it, in the web UI, in the terminal, or by simply asking Dcode. PostgreSQL, MySQL / MariaDB and SQLite are supported; the drivers are built in, so nothing has to be installed on the server.

What a connection may do is decided by the database. Dcode logs in as the database user you give it and has exactly that user's rights: tables the user can't read don't even show up. A read-only user is a good default.

Add a connection

  • Web UI: Databases in the sidebar → New connection. Fill in host, port, database, user and password, press Test, then Save.
  • Terminal: /db add asks the same questions, or give it all at once as a URL.
  • The password is stored only on your machine, in a file only you can read, and is never shown again. You can name an environment variable to take it from instead.
  • Encryption is automatic: TLS when the server offers it. You can require it, or require a verified certificate.
terminal
/db add shop postgres://analyst:secret@db.internal:5432/shop
/db shop                      tables with their sizes
/db shop orders               one table: columns, keys, indexes
/db shop SELECT status, count(*) FROM orders GROUP BY status
/db shop summary              size, biggest tables, heavy tables
/db shop export orders        to a CSV file (also: export schema, export all)

The Databases screen

  • Tables on the left with their row counts; click one to see its Data (first 100 rows) and Structure (columns, keys, indexes).
  • SQL: write a statement and press Ctrl/⌘+Enter. Results appear in a grid.
  • Summary: total size, number of tables, the largest tables, tables without a primary key, and a button to have Dcode write a summary of the whole database.
  • Export: a table or a query's full result as CSV or JSON lines, the structure as Markdown, or the whole database as a zip of CSV files. Files are kept in ~/.dcode/db/exports.

Ask Dcode

When at least one connection is saved, Dcode can read the structure and run queries itself. It counts and groups in SQL instead of pulling rows into the chat.

try it
In the shop database, which 10 customers spent the most last month? Save the list as top-customers.csv.

Guards

GuardWhat it does
Reads are read-onlyQueries run in a read-only session, one statement at a time. The database itself refuses anything that would write.
Changes ask every timeINSERT, UPDATE, DELETE, DROP and anything else that isn't a plain read is shown to you first and runs only after you confirm it. This holds in every mode, including auto, and can't be allowed "for the session". Plan mode refuses changes.
Read-only in DcodeA switch on each connection that refuses every change through it, whatever the database user may do.
Row and time limitsA query returns at most 200 rows and is cancelled after 30 seconds.
Heavy tablesA table estimated above 1,000,000 rows or 200 MB is not exported whole: Dcode tells you and offers to export only what fits. Every export also stops at those limits and when the disk is nearly full.

Change the limits, or stop Dcode from using your connections, in Settings → Permissions → Databases.

11Scheduled jobs

Run something on a schedule and read its output afterwards. A job is either a shell command (like crontab) or a Dcode prompt: a task Dcode does by itself, for example checking logs every morning and writing a report.

  • Web UI: Scheduled in the sidebar → New job. Pick a common schedule or type one; the page shows the next run times as you type.
  • Terminal: /cron add asks a few questions, or give the schedule and the command directly.
  • Every run keeps a log with its output, result and duration. The last 50 runs of each job are kept.
  • Run now starts a job at once; the switch turns it off without deleting it; a running job can be stopped.
terminal
/cron add "30 2 * * *" pg_dump -Fc shop > /backups/shop.dump
/cron                         jobs, next run, last result
/cron run <id>   ·   /cron logs <id>
/cron off <id>   ·   /cron on <id>   ·   /cron rm <id>

Schedules

A schedule has five fields: minute, hour, day of month, month, day of week. Times are the machine's local time.

ScheduleRuns
*/15 * * * *every 15 minutes
0 * * * * or @hourlyevery hour
30 2 * * *every day at 02:30
0 9 * * 1-5Monday to Friday at 09:00
0 4 1 * *on the 1st of every month at 04:00

Good to know

  • Jobs run in the background, even with no terminal open: Dcode's background service stays up while at least one job is switched on. After a reboot it starts again the next time you run dcode. Runs that were due while it was down are not caught up.
  • If a job is still running when its next time comes, that run is skipped and noted in the log. A run is stopped after its time limit (60 minutes unless you change it).
  • A Dcode prompt runs unattended. Nobody is there to approve anything, so whatever would ask is refused, and the run is marked failed. Choose what the job may do: read only, edit files, or edit files and run commands. Your rules still apply.
  • Jobs are yours alone: they live in ~/.dcode/cron, a project folder can't add one, and Dcode can't create one for itself.
  • The same unattended mode is available to you: dcode run --mode auto "update the changelog".

12Tips for small models (32K or less)

  • Give clear, specific tasks: "add input validation to api/users.py" works better than "improve the code".
  • Keep helpers on. Exploration happens outside the main context, so long sessions stay accurate.
  • Put project rules in a DCODE.md (or AGENTS.md) file at the repo root. Dcode reads it automatically.
  • Pin only one or two skills. Unpinned skills cost almost nothing until they're used.
  • Watch the context ring in the web UI. Dcode tidies the conversation automatically at around 75% full.
  • Start a /new chat when you switch to an unrelated task.

14Security

  • Folder sandbox: file tools stay in the project folder. If Dcode needs a file outside it, it asks first.
  • Approvals: commands, deletions and commits always ask first, unless you turn on auto-approve (only for trusted, sandboxed machines).
  • Rules: exceptions to the mode, by pattern, in Settings → Permissions or with /rules. Allow runs without asking (e.g. git status*), ask always asks even in auto mode (e.g. git push*), deny refuses (e.g. rm -rf *). .env files are protected by default. A project can add stricter rules in .dcode/rules.json, but never allow anything itself.
  • Hooks: your own shell commands before or after a tool, when a task is done, or when Dcode needs an answer: block risky commands, keep an audit log, get a desktop notification. They're set in your own settings only, never by a project.
  • Private web UI: it listens only on 127.0.0.1 and needs a secret per-user link. Other users on the same server can't see or control your sessions.
  • Secrets: ~/.dcode is readable only by you, and the web UI never shows your API key.
  • Databases: Dcode has the rights of the database user you connect with, nothing more. Reads are read-only, and every change is shown to you and needs your confirmation, in every mode. Saved passwords are never shown.
  • Scheduled jobs can only be created by you. A Dcode prompt that runs on a schedule can't get approvals, so anything that would ask is refused.
  • Artifacts run in a sandbox with no network access.

Dcode یک دستیار برنامه‌نویسی هوشمند است که در ترمینال اجرا می‌شود و یک رابط وب هماهنگ هم دارد. با مدل‌های زبانی محلی یا خصوصی خودتان کار می‌کند و برای مدل‌هایی با پنجرهٔ زمینهٔ کوچک (۳۲ هزار توکن یا کمتر) ساخته شده است. در این راهنما نصب، اتصال به مدل و استفادهٔ روزمره را توضیح می‌دهیم.

۱Dcode چه کار می‌کند؟

به زبان ساده بنویسید: «تست خراب را درست کن»، «یک endpoint سلامت اضافه کن» یا «این مخزن را توضیح بده». Dcode کد شما را می‌خواند، فایل‌ها را ویرایش می‌کند، دستور اجرا می‌کند و git را بررسی می‌کند. همهٔ مراحل را نشان می‌دهد و قبل از هر کار پرخطری از شما اجازه می‌گیرد.

مدل خودتان، شبکهٔ خودتانبا Ollama، vLLM، llama.cpp، LM Studio، TGI یا هر سرور سازگار با OpenAI کار می‌کند. هیچ داده‌ای از شبکهٔ شما خارج نمی‌شود.
هوشمند با زمینهٔ کوچکفقط خطوط لازم را می‌خواند، خروجی‌های قدیمی را کوتاه و گفتگوهای طولانی را خلاصه می‌کند تا مدل‌های ۳۲K دقیق بمانند.
دستیارهای کمکی (Sub-agent)کارهای مشخص را به دستیارهای کمکی (کاوشگر، کدنویس، بازبین، تستر) می‌سپارد که هر کدام با ذهنی خالی شروع می‌کنند.
حافظه، آرتیفکت‌ها، مهارت‌هاقواعد پروژهٔ شما را به خاطر می‌سپارد، صفحه و نمودار برایتان می‌سازد و از دستورالعمل‌های قابل‌استفادهٔ مجدد پیروی می‌کند.

۴کار با ترمینال

در پوشهٔ پروژه یک ترمینال باز کنید و dcode را اجرا کنید. پنل خوش‌آمد مدل، پوشه و لینک رابط وب را نشان می‌دهد. خواسته‌تان را بنویسید و Enter بزنید.

  • هر مرحله به شکل یک خط مثل ⏺ read_file app.py نمایش داده می‌شود. وقتی کار تمام شد، Dcode یک گزارش کوتاه می‌نویسد (چه کرد، کدام فایل‌ها تغییر کرد، چه دستورهایی اجرا شد) و بعد خطی مثل ✓ Done in 3.2s · 2 files changed · 3 commands می‌آید.
  • کادر ورودی با تایپ شما بزرگ می‌شود. با Enter بفرستید؛ ⌥ Option/Alt+Enter (یا \ و بعد Enter) خط جدید می‌سازد؛ با ↑/↓ پیام‌های قبلی را برگردانید.
  • وقتی Dcode در حال کار است، Ctrl+C کار جاری را متوقف می‌کند و گفتگو سالم می‌ماند. در کادر خالی، Ctrl+C را دو بار بزنید تا خارج شوید.
  • هر گفتگو به‌طور خودکار از روی اولین پیام شما نام‌گذاری می‌شود. نام زیر کادر ورودی و در رابط وب دیده می‌شود.
  • وقتی Dcode بخواهد دستوری اجرا کند، فایلی را حذف کند یا commit بزند، یک منو باز می‌شود. با کلیدهای جهت و Enter انتخاب کنید، یا y (اجازه)، a (اجازه برای کل این نشست) یا n (رد) را بزنید.
  • در فهرست‌های بلند، مثل فهرست مدل‌ها، کافی است تایپ کنید تا فیلتر شود.
  • اشاره به فایل با @: @ و بخشی از نام فایل را تایپ کنید و با Tab یا Enter انتخاب کنید، مثلاً fix the bug in @src/app.py. تا ۳ فایلِ اشاره‌شده مستقیم وارد گفتگو می‌شوند و Dcode برای پیدا کردنشان مرحله‌ای خرج نمی‌کند. در رابط وب هم کار می‌کند.
  • برای کارهای طولانی‌تر، Dcode یک چک‌لیست (☰) نگه می‌دارد و مرحله‌ها را تیک می‌زند. این فهرست بعد از فشرده‌سازی زمینه هم می‌ماند تا مدل‌های کوچک مسیر را گم نکنند.
  • وقتی چیزی واقعاً مبهم باشد، Dcode ممکن است از شما سؤالی بپرسد و چند گزینه بدهد. یکی را انتخاب کنید، پاسخ خودتان را بنویسید، یا Esc را بزنید تا خودش تصمیم بگیرد.

دستورهای خودتان

پرامپتی را که زیاد استفاده می‌کنید در یک فایل Markdown ذخیره کنید تا به یک دستور تبدیل شود. فایل .dcode/commands/review-pr.md در پروژه (یا ~/.dcode/commands/ برای همهٔ پروژه‌ها) دستور /review-pr را می‌سازد:

.dcode/commands/review-pr.md
---
description: Review my branch against main
agent: review            # optional: run it as this helper
---
Review these changes for bugs and missing tests. Focus: $ARGUMENTS
!`git diff main...HEAD --stat`
Our conventions are in @CONTRIBUTING.md

$ARGUMENTS همان چیزی است که بعد از دستور تایپ می‌کنید ($1، $2… کلمه‌به‌کلمه). !`command` خروجی آن دستور را داخل پرامپت می‌گذارد؛ این دستورها هم تابع همان حالت و قوانینِ دستورهای خود Dcode هستند و اگر مجاز نباشند اول اجازه می‌گیرند.

حالت‌ها

در کادر ورودی با Shift+Tab بین حالت‌ها جابه‌جا شوید. حالت فعلی زیر کادر نمایش داده می‌شود و رنگ حاشیه هم با آن عوض می‌شود. در رابط وب هم کنار کادر پیام می‌توانید حالت را انتخاب کنید.

حالتDcode چه کاری می‌تواند بکند
🔵 پذیرش ویرایش‌ها (پیش‌فرض)فایل‌ها را آزادانه ویرایش می‌کند؛ برای دستور، حذف و commit اجازه می‌گیرد
🟢 خودکار (Auto)هیچ‌وقت نمی‌پرسد. فقط در پروژه‌های مطمئن یا ایزوله
🟣 برنامه‌ریزی (Plan)فقط‌خواندنی: بررسی می‌کند و برنامه می‌نویسد، بعد می‌پرسد «آیا این برنامه اجرا شود؟»
⚪ دستی (Manual)قبل از هر ویرایش و هر دستور اجازه می‌گیرد

خروجی، بازگردانی و git

  • خروجی دستورها فقط چند خط اول را نشان می‌دهد. با Ctrl+O در کادر ورودی، خروجی کامل آخرین کار را ببینید.
  • هر ویرایش یک پیش‌نمایش قرمز/سبز از تغییرات نشان می‌دهد.
  • بررسی بعد از ویرایش: Dcode بلافاصله بعد از تغییر هر فایل، آن را با ابزارهایی که روی سیستم دارید بررسی می‌کند (خطای نحوی، نام‌های تعریف‌نشده): خود پایتون، ruff، node، bash، gofmt و غیره. مشکل‌ها مستقیم به مدل برمی‌گردند و در مرحلهٔ بعد رفع می‌شوند. برای اجرای فرمتر هم، گزینهٔ Also format them را در تنظیمات ← مجوزها روشن کنید.
  • وقتی Dcode کار می‌کند، یک پنل زنده مرحلهٔ فعلی، دستیارهای در حال کار و کارهای پس‌زمینه را با زمان‌سنج نشان می‌دهد. دستورهای طولانی (سرورها، watcherها) به‌صورت کار پس‌زمینه اجرا می‌شوند؛ خط وضعیت تعدادشان را نشان می‌دهد و با /jobs مدیریت می‌شوند. با خروج از Dcode متوقف می‌شوند.
  • هر کار یک نقطهٔ بازگشت ذخیره می‌کند. /undo فایل‌ها را به حالت قبل برمی‌گرداند، حتی بیرون از git.
  • /diff تغییرات commit‌نشده را نشان می‌دهد و /commit از روی diff یک پیام commit می‌نویسد و قبل از commit اجازه می‌گیرد.

۵کار با رابط وب

هر dcode که اجرا می‌کنید یک صفحهٔ خصوصی هم روی سیستم خودتان باز می‌کند. لینک را از پنل خوش‌آمد باز کنید (یا dcode ui را بزنید). روی سرور مشترک، هر کاربر صفحهٔ خصوصی خودش را دارد.

  • نوار کناری: نشست‌های فعال در بالا، گفتگوهای قبلی دسته‌بندی‌شده بر اساس تاریخ، جستجو و گفتگوی جدید (⌘/Ctrl ⇧ O).
  • گفتگو: کار را به همان نشستی بفرستید که در ترمینال باز است. مراحل در «N مرحله انجام شد» جمع می‌شوند و دستیارها به شکل کارت دیده می‌شوند.
  • تأییدها: اجازه، اجازه برای این نشست یا رد، از مرورگر یا ترمینال. هر کدام زودتر پاسخ دهد اعمال می‌شود.
  • منوی مدل (بالا سمت چپ): مدل‌های سرور را جستجو کنید یا هر نامی را تایپ کنید؛ سطح استدلال را تنظیم کنید.
  • تنظیمات: اتصال، مدل، دستیارها، حافظه، مجوزها، مهارت‌ها و پوستهٔ روشن/تیره/سیستم.
💡

چند ثانیه پس از بسته شدن آخرین dcode، صفحه خودش بسته می‌شود. گفتگوها، حافظه و آرتیفکت‌ها روی دیسک می‌مانند و دفعهٔ بعد دوباره دیده می‌شوند.

۶دستیارهای کمکی (Sub-agent)

برای کارهای بزرگ‌تر، Dcode کارهای مستقل را به دستیارهای کمکی می‌سپارد. هر کدام با زمینهٔ خالی شروع می‌کند و فقط یک گزارش کوتاه برمی‌گرداند؛ به این ترتیب گفتگوی اصلی کوچک و متمرکز می‌ماند.

دستیارمناسب برای
🧭 کاوشگر (Explorer)پیدا کردن و خواندن کد و گزارش با ارجاع فایل:خط (فقط‌خواندنی)
💻 کدنویس (Coder)انجام یک تغییر مشخص
👁 بازبین (Reviewer)بررسی کد یا diff برای یافتن باگ (فقط‌خواندنی)
🧪 تستر (Tester)نوشتن و اجرای تست

دستیارهای فقط‌خواندنی می‌توانند همزمان کار کنند. تعدادشان را در /agents settings یا تنظیمات ← دستیارها تعیین کنید. اجرای همزمان بیش از یکی به سروری نیاز دارد که درخواست‌های همزمان را پشتیبانی کند (vLLM یا llama-server --parallel N).

  • استفادهٔ مستقیم: پیام را با @name شروع کنید، مثلاً @explore where is the login handled?. فقط گزارش آن برمی‌گردد.
  • مدل جدا برای دستیارها: در تنظیمات ← دستیارها، Helper model را تنظیم کنید تا دستیارها روی مدلی کوچک‌تر و سریع‌تر از همان سرور اجرا شوند و گفتگوی اصلی همان مدل بزرگ را نگه دارد.
  • دستیار خودتان را بسازید: یک فایل Markdown در ~/.dcode/agents/ یا پوشهٔ .dcode/agents/ پروژه بگذارید، یا از New helper در تنظیمات ← دستیارها استفاده کنید. فایلی با نام یک دستیار پیش‌فرض (مثل explore.md) همان دستیار را تغییر می‌دهد.
.dcode/agents/ansible.md
---
description: Reviews Ansible playbooks for idempotency and secrets
tools: read-only          # or: edit, or a list like read_file, run_command
model: qwen2.5-coder:7b   # optional
steps: 20                 # optional
---
You review Ansible code. Check every task for idempotency, ...

۷حافظه

Dcode اطلاعات مفید را بین نشست‌ها به خاطر می‌سپارد: قواعد پروژه، روش اجرای تست‌ها، ترجیحات شما و خلاصهٔ کارهای قبلی. حافظه‌های مرتبط به‌طور خودکار به هر کار جدید اضافه می‌شوند.

  • مستقیم بگویید: «یادت باشد ما با make release منتشر می‌کنیم»، یا از /remember استفاده کنید.
  • حافظه‌ها را در رابط وب ببینید، اضافه یا حذف کنید (نوار کناری ← حافظه).
  • همه‌چیز به شکل Markdown ساده در ~/.dcode/memory/ ذخیره می‌شود، برای هر پروژه یا به‌صورت عمومی. جستجو آفلاین و بدون مدل embedding انجام می‌شود.

۸آرتیفکت‌ها

وقتی چیزی برای دیدن می‌خواهید، مثل داشبورد، نمودار، گزارش یا یک اسکریپت بلند، Dcode آن را به‌جای چسباندن در گفتگو به‌عنوان یک آرتیفکت ذخیره می‌کند.

  • یک کارت در گفتگو ظاهر می‌شود. روی Open بزنید تا در پنل کناری با زبانه‌های پیش‌نمایش و کد، کپی و دانلود باز شود.
  • همهٔ آرتیفکت‌ها در کتابخانهٔ Artifacts در نوار کناری هستند.
  • انواع: صفحهٔ وب (HTML)، نمودار (SVG)، سند (Markdown)، جدول (CSV) و کد.
  • صفحه‌ها در یک محیط ایزوله و بدون دسترسی به اینترنت اجرا می‌شوند. هر به‌روزرسانی نسخهٔ قبلی را نگه می‌دارد.

مدیریت آرتیفکت‌ها

  • کتابخانه: پیش‌نمایش زنده، جستجو، فیلتر بر اساس نوع و مرتب‌سازی. منوی هر کارت گزینه‌های باز کردن، باز کردن به‌صورت صفحه، کپی لینک، تغییر نام، تکثیر، دانلود و حذف را دارد.
  • نمایشگر: زبانه‌های پیش‌نمایش، کد و ویرایش (ذخیره یک نسخهٔ جدید می‌سازد). هر نسخه‌ای را از تاریخچه انتخاب و بازیابی کنید. برای تغییر نام روی عنوان بزنید و با لینک کنار آن به گفتگویی که آرتیفکت را ساخته برگردید.
  • تغییر توسط Dcode: درخواست خود را در کادر زیر نمایشگر بنویسید تا Dcode همان آرتیفکت را به‌عنوان نسخهٔ جدید به‌روز کند.
  • آرتیفکت جدید: از Dcode بخواهید بسازد، خودتان بنویسید یا بچسبانید، یا یک فایل بارگذاری کنید (HTML، SVG، Markdown، CSV یا هر نوع کد).
  • لینک‌ها: هر آرتیفکت صفحهٔ مخصوص خودش را در /a/<id> دارد. وقتی Dcode در ترمینال یک آرتیفکت ذخیره می‌کند لینکش چاپ می‌شود، و /artifacts فهرست آن‌ها را نشان می‌دهد و هر کدام را در مرورگر باز می‌کند.

۹مهارت‌ها (Skills)

مهارت‌ها دستورالعمل‌های کوتاهی هستند که روش کار Dcode را شکل می‌دهند. فقط نام و توضیح یک‌خطی آن‌ها در prompt است و Dcode هر وقت مهارتی به کار بخورد، متن کاملش را بارگذاری می‌کند. به همین دلیل حتی روی مدل‌های کوچک هم کم‌هزینه‌اند. با سنجاق کردن، یک مهارت همیشه به کار گرفته می‌شود.

ساختن مهارت دلخواه

  1. از Dcode بخواهید: «یک مهارت برای نوشتن playbookهای Ansible به روش تیم ما بساز». Dcode خودش آن را می‌نویسد و ذخیره می‌کند.
  2. در رابط وب: تنظیمات ← مهارت‌ها ← Create (نوشتن توسط Dcode) یا Write one yourself (نوشتن دستی).
  3. به‌صورت فایل: یک فایل .md در ~/.dcode/skills/ بگذارید، یا در .dcode/skills/ داخل پروژه تا از طریق git با تیم به اشتراک گذاشته شود.
~/.dcode/skills/ansible.md
---
name: ansible
description: Writing Ansible playbooks and roles our team's way.
---
# Ansible
- Use roles; one role per service.
- Every task has a name and tags.
- Secrets come from ansible-vault, never plain text.
- Check with --check --diff before applying.

۱۰پایگاه‌های داده

اتصال به یک پایگاه داده را یک بار ذخیره کنید؛ بعد می‌توانید آن را مرور کنید، کوئری بگیرید، خلاصه‌اش را ببینید و خروجی بگیرید: در رابط وب، در ترمینال، یا فقط با پرسیدن از Dcode. از PostgreSQL، MySQL / MariaDB و SQLite پشتیبانی می‌شود و درایورها داخل خود Dcode هستند؛ لازم نیست چیزی روی سرور نصب شود.

اینکه یک اتصال چه کاری می‌تواند بکند را خودِ پایگاه داده تعیین می‌کند. Dcode با همان کاربری که می‌دهید وارد می‌شود و دقیقاً دسترسی‌های همان کاربر را دارد: جدول‌هایی که آن کاربر اجازهٔ خواندنشان را ندارد اصلاً نمایش داده نمی‌شوند. یک کاربر فقط‌خواندنی انتخاب خوبی برای شروع است.

افزودن اتصال

  • رابط وب: در نوار کناری Databases → New connection. میزبان، پورت، نام پایگاه، کاربر و رمز را وارد کنید، Test را بزنید و بعد Save.
  • ترمینال: /db add همین سؤال‌ها را می‌پرسد؛ یا همه را یک‌جا به شکل URL بدهید.
  • رمز فقط روی دستگاه خودتان و در فایلی که فقط شما می‌توانید بخوانید ذخیره می‌شود و دیگر نمایش داده نمی‌شود. می‌توانید به‌جای آن نام یک متغیر محیطی را بدهید.
  • رمزنگاری خودکار است: اگر سرور TLS داشته باشد استفاده می‌شود. می‌توانید آن را اجباری کنید یا تأیید گواهی را هم بخواهید.
terminal
/db add shop postgres://analyst:secret@db.internal:5432/shop
/db shop                      tables with their sizes
/db shop orders               one table: columns, keys, indexes
/db shop SELECT status, count(*) FROM orders GROUP BY status
/db shop summary              size, biggest tables, heavy tables
/db shop export orders        to a CSV file (also: export schema, export all)

صفحهٔ Databases

  • جدول‌ها در سمت کنار با تعداد سطرهایشان؛ روی هر کدام بزنید تا Data (۱۰۰ سطر اول) و Structure (ستون‌ها، کلیدها، ایندکس‌ها) را ببینید.
  • SQL: دستور را بنویسید و Ctrl/⌘+Enter بزنید. نتیجه در یک جدول نمایش داده می‌شود.
  • Summary: حجم کل، تعداد جدول‌ها، بزرگ‌ترین جدول‌ها، جدول‌های بدون کلید اصلی، و دکمه‌ای که از Dcode می‌خواهد خلاصه‌ای از کل پایگاه بنویسد.
  • Export: یک جدول یا نتیجهٔ کامل یک کوئری به شکل CSV یا JSON lines، ساختار به شکل Markdown، یا کل پایگاه به شکل یک فایل zip از CSVها. فایل‌ها در ~/.dcode/db/exports می‌مانند.

وقتی دست‌کم یک اتصال ذخیره شده باشد، Dcode خودش می‌تواند ساختار را بخواند و کوئری اجرا کند. به‌جای آوردن سطرها به گفتگو، شمارش و گروه‌بندی را در خود SQL انجام می‌دهد.

محافظ‌ها

محافظچه می‌کند
خواندن فقط‌خواندنی استکوئری‌ها در یک نشست فقط‌خواندنی و هر بار یک دستور اجرا می‌شوند. خودِ پایگاه داده هر چیزی را که بخواهد بنویسد رد می‌کند.
تغییرها هر بار پرسیده می‌شوندINSERT، UPDATE، DELETE، DROP و هر چیزی که خواندنِ ساده نباشد اول به شما نشان داده می‌شود و فقط بعد از تأیید شما اجرا می‌شود. این در همهٔ حالت‌ها، حتی auto، برقرار است و نمی‌توان آن را «برای کل نشست» مجاز کرد. حالت plan تغییرها را رد می‌کند.
فقط‌خواندنی در Dcodeکلیدی روی هر اتصال که هر تغییری از طریق آن را رد می‌کند، هر دسترسی‌ای که کاربر پایگاه داشته باشد.
سقف سطر و زمانهر کوئری حداکثر ۲۰۰ سطر برمی‌گرداند و بعد از ۳۰ ثانیه لغو می‌شود.
جدول‌های سنگینجدولی که تخمین زده شود بیش از ۱٬۰۰۰٬۰۰۰ سطر یا ۲۰۰ مگابایت دارد کامل خروجی گرفته نمی‌شود: Dcode خبر می‌دهد و پیشنهاد می‌کند فقط همان مقداری که جا می‌شود خروجی بگیرد. هر خروجی هم در همین سقف‌ها، و وقتی دیسک تقریباً پر است، متوقف می‌شود.

سقف‌ها را در Settings → Permissions → Databases تغییر دهید؛ همان‌جا می‌توانید استفادهٔ Dcode از اتصال‌هایتان را هم خاموش کنید.

۱۱کارهای زمان‌بندی‌شده

چیزی را طبق زمان‌بندی اجرا کنید و بعداً خروجی‌اش را بخوانید. هر کار یا یک دستور شل است (مثل crontab) یا یک درخواست از Dcode: کاری که Dcode خودش انجام می‌دهد، مثلاً هر صبح لاگ‌ها را بررسی کند و گزارش بنویسد.

  • رابط وب: در نوار کناری Scheduled → New job. یک زمان‌بندی رایج را انتخاب کنید یا خودتان بنویسید؛ همان موقع زمان اجراهای بعدی نمایش داده می‌شود.
  • ترمینال: /cron add چند سؤال می‌پرسد؛ یا زمان‌بندی و دستور را مستقیم بدهید.
  • هر اجرا یک لاگ با خروجی، نتیجه و مدت‌زمان دارد. ۵۰ اجرای آخر هر کار نگه داشته می‌شود.
  • Run now کار را همان لحظه اجرا می‌کند؛ با کلید می‌توانید آن را بدون حذف خاموش کنید؛ کارِ در حال اجرا را می‌توان متوقف کرد.
terminal
/cron add "30 2 * * *" pg_dump -Fc shop > /backups/shop.dump
/cron                         jobs, next run, last result
/cron run <id>   ·   /cron logs <id>
/cron off <id>   ·   /cron on <id>   ·   /cron rm <id>

خوب است بدانید

  • کارها در پس‌زمینه اجرا می‌شوند، حتی وقتی هیچ ترمینالی باز نیست: تا وقتی دست‌کم یک کار روشن باشد، سرویس پس‌زمینهٔ Dcode بالا می‌ماند. بعد از ری‌استارت دستگاه، دفعهٔ بعدی که dcode را اجرا کنید دوباره شروع می‌شود. اجراهایی که در زمان خاموش‌بودن سرویس موعدشان بوده جبران نمی‌شوند.
  • اگر کاری هنوز در حال اجرا باشد و نوبت بعدی‌اش برسد، آن نوبت رد می‌شود و در لاگ ثبت می‌شود. هر اجرا بعد از سقف زمانی‌اش متوقف می‌شود (۶۰ دقیقه، مگر اینکه تغییرش دهید).
  • درخواست از Dcode بدون حضور شما اجرا می‌شود. کسی نیست که چیزی را تأیید کند؛ پس هر کاری که نیاز به تأیید داشته باشد رد می‌شود و آن اجرا ناموفق ثبت می‌شود. خودتان تعیین کنید کار چه اجازه‌ای دارد: فقط خواندن، ویرایش فایل‌ها، یا ویرایش فایل‌ها و اجرای دستورها. قوانین شما همچنان اعمال می‌شوند.
  • کارها فقط مال شما هستند: در ~/.dcode/cron نگه داشته می‌شوند، پوشهٔ یک پروژه نمی‌تواند کاری اضافه کند و Dcode هم نمی‌تواند برای خودش کاری بسازد.
  • همین حالتِ بدون‌حضور برای خودتان هم در دسترس است: dcode run --mode auto "update the changelog".

۱۲نکته‌هایی برای مدل‌های کوچک (۳۲K یا کمتر)

  • کارهای واضح و مشخص بدهید: «به api/users.py اعتبارسنجی ورودی اضافه کن» بهتر از «کد را بهتر کن» جواب می‌دهد.
  • دستیارهای کمکی را روشن نگه دارید؛ کاوش بیرون از زمینهٔ اصلی انجام می‌شود و نشست‌های طولانی دقیق می‌مانند.
  • قواعد پروژه را در فایل DCODE.md (یا AGENTS.md) در ریشهٔ مخزن بنویسید؛ Dcode خودکار آن را می‌خواند.
  • فقط یکی دو مهارت را سنجاق کنید؛ مهارت‌های سنجاق‌نشده تا وقتی استفاده نشوند تقریباً هزینه‌ای ندارند.
  • حلقهٔ زمینه را در رابط وب زیر نظر داشته باشید؛ Dcode حدود ۷۵٪ پر شدن، گفتگو را خودکار مرتب می‌کند.
  • وقتی سراغ کاری بی‌ارتباط می‌روید، با /new گفتگوی تازه شروع کنید.

تنظیمات در ~/.dcode/config.json ذخیره می‌شوند و می‌توانید آن‌ها را در رابط وب یا با دستورهای اسلش تغییر دهید. متغیرهای محیطی بر فایل اولویت دارند و رابط وب آن فیلدها را فقط‌خواندنی نشان می‌دهد.

۱۴امنیت

  • محدودیت پوشه: ابزارهای فایل داخل پوشهٔ پروژه می‌مانند. اگر Dcode به فایلی بیرون از آن نیاز داشته باشد، اول اجازه می‌گیرد.
  • تأییدها: اجرای دستور، حذف فایل و commit همیشه اول اجازه می‌گیرند، مگر تأیید خودکار را روشن کنید (فقط برای سیستم‌های مطمئن و ایزوله).
  • قوانین: استثناهایی بر حالت فعلی، بر اساس الگو، در تنظیمات ← مجوزها یا با /rules. Allow بدون پرسیدن اجرا می‌کند (مثلاً git status*)، Ask همیشه می‌پرسد، حتی در حالت خودکار (مثلاً git push*)، و Deny رد می‌کند (مثلاً rm -rf *). فایل‌های .env به‌طور پیش‌فرض محافظت می‌شوند. هر پروژه می‌تواند در .dcode/rules.json قوانین سخت‌گیرانه‌تری اضافه کند، ولی هرگز نمی‌تواند به خودش اجازه بدهد.
  • Hookها: دستورهای shell خودتان، قبل یا بعد از یک ابزار، وقتی کاری تمام شد یا وقتی Dcode منتظر پاسخ شماست: مسدود کردن دستورهای پرخطر، ثبت گزارش، اعلان دسکتاپ. فقط در تنظیمات خودتان تعریف می‌شوند، نه توسط پروژه.
  • رابط وب خصوصی: فقط روی 127.0.0.1 در دسترس است و یک لینک مخفی مخصوص هر کاربر لازم دارد. کاربران دیگر همان سرور نمی‌توانند نشست‌های شما را ببینند یا کنترل کنند.
  • اسرار: پوشهٔ ~/.dcode فقط برای شما خواندنی است و رابط وب هیچ‌وقت کلید API را نشان نمی‌دهد.
  • پایگاه‌های داده: Dcode دقیقاً دسترسی‌های همان کاربر پایگاه داده‌ای را دارد که با آن وصل می‌شوید، نه بیشتر. خواندن‌ها فقط‌خواندنی‌اند و هر تغییری، در هر حالتی، اول به شما نشان داده می‌شود و تأیید شما را می‌خواهد. رمزهای ذخیره‌شده هیچ‌وقت نمایش داده نمی‌شوند.
  • کارهای زمان‌بندی‌شده را فقط خودتان می‌توانید بسازید. درخواستی که طبق زمان‌بندی به Dcode داده می‌شود نمی‌تواند تأیید بگیرد؛ پس هر چیزی که نیاز به تأیید داشته باشد رد می‌شود.
  • آرتیفکت‌ها در محیط ایزوله و بدون دسترسی به شبکه اجرا می‌شوند.

مشکلراه‌حل
